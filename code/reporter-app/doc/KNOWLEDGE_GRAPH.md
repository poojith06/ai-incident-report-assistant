# Knowledge graph: offline post-incident analysis

Spec: `doc/specs/KNOWLEDGE_GRAPH_SPEC.md` (the user's design). Core principle: **the graph selects approved facts and actions; the LLM may
only rephrase them; Kotlin validates every output.** Everything runs offline in the app; nothing here changes extraction, severity,
follow-up questions or submission.

## Data flow
```mermaid
flowchart LR
  Sub[Report submitted] --> Adapter[KnowledgeGraphInput\nIncidentReport -> ValidatedIncident]
  Saved[(Saved reports)] --> Hist[HistoryPatternDetector\nHistoricalPattern nodes]
  Adapter --> Engine[KnowledgeGraphEngine.analyze]
  Hist -->|citations| Engine
  Pack[(Active GraphPack\nfiles/kg/packs/N.json)] --> Engine
  Engine --> Rules[SafetyPolicy / MedicalOutputGuard\nphone guard / approval + expiry]
  Engine --> Render[GroundedRecommendationRenderer\nTemplate (default) or LLM + validator]
  Render --> Audit[(files/kg/audit/id.json)]
  Render --> Outbox[(files/kg/outbox/id.json)]
  Render --> UI[Success screen:\nPost-incident analysis card]
  Outbox -.future sync.-> Dash[Admin dashboard]
  Dash -.GraphPack import.-> Pack
```
`KnowledgeGraphService.analyze(report, savedReports)` runs it off the main thread after the submit succeeded (`IncidentFlowViewModel.startAnalysis`),
never throws (a failure is `AnalysisResult.Failed`, shown as "analysis not available") and is switched by Settings > "Post-incident analysis" (default on).

## The engine in short (spec sections 10 to 13)
1. Reject an incident the user has not confirmed (only SUBMITTED reports; `userConfirmed`). Abstain below `abstainBelowEvidence` (0.3) with the question "can you confirm".
2. Resolve the incident type node by `code`. Unknown type: abstain + question. Location type, assets and status are never guessed.
3. Traverse ONLY the whitelisted paths: incident type -TRIGGERS_ACTION-> action; type -PRODUCES_HAZARD-> hazard -MAY_CAUSE-> consequence
   -REQUIRES_ACTION-> action; location type -HAS_CONTINUITY_OPTION-> temporary arrangement; asset type -REQUIRES_ACTION-> action;
   action -OWNED_BY-> team; recommendation -SUPPORTED_BY-> source; historical pattern -TRIGGERS_ACTION-> action; action -DEPENDS_ON-> prerequisite.
4. Edge conditions (`EdgeConditions`): incidentTypes, locationTypes, assetTypes, statuses, hazardsAny/All/None, min/maxSeverity, injury, minPeopleAffected,
   operationalEffectsAny, minEvidenceConfidence. A condition on an unknown fact FAILS and names the fact; the most useful missing fact becomes the ONE unresolved question.
5. Hard filters (each removal is logged with its reason): inactive/disabled; edge or recommendation not APPROVED (reporters); recommendation expired; source missing,
   rejected, expired, or not APPROVED (reporters); approval record incomplete; authorized-only action addressed to the reporter; unsafe wording for the reporter
   (enter danger, fight fire, touch or operate electrical equipment, utility shut-offs, handle or clean up chemicals, restart damaged equipment); medical content
   (diagnosis, medicine, dosage, treatment, home remedy); unverified phone number; unavailable prerequisite or prerequisite cycle; duplicate canonical key.
6. Rank: 0.30 graph priority + 0.20 severity relevance + 0.15 location match + 0.15 asset match + 0.10 recurrence + 0.10 evidence completeness (weights configurable).
   Order: life safety > hazard isolation > responder escalation > service continuity > evidence preservation > restoration > prevention; prerequisites always first.
7. Limits: 3 immediate, 3 operational, 3 recovery, 2 temporary arrangements, 2 preventive, 1 question, 4 consequences. Consequences are tagged POSSIBLE / LIKELY (hazard
   reported active) / CONFIRMED (the pack says an operational effect proves it and the report has it); never certain otherwise.
8. Audience: `REPORTER` (APPROVED recommendation on an APPROVED, unexpired source) or `ADMIN_PREVIEW` (draft/reviewed/unverified also, labelled `unverifiedDraft`). Safety, medical,
   phone and expiry filters apply to BOTH.

## Demo guidance (important)
Every seed source except `sop:demo-seed:v1` is `NEEDS_ADMIN_VERIFICATION`, so by the spec rule ordinary users would see nothing. To make the feature demonstrable the
seed has ONE source `sop:demo-seed:v1`, status APPROVED, `approvedBy = "demo-seed (not a real SOP)"`, shown with the label **"Demo guidance - pending IIIT-H admin approval"**
in the card and in every export (`guidanceLabel`, `sourceLabel`). It is NOT a real IIIT-H procedure. Admins replace it: attach real SOPs (`attachSource`), approve the
recommendations on them (`approveRecommendation`), then expire or reject the demo source. The recommendations that need a real procedure cite the unverified placeholder
sources as DRAFT, so only the admin preview shows them. See ADR-055 and `assets/kg/README.md`.

## How to add a scenario (data only, no Kotlin)
1. Add an `INCIDENT_TYPE` node (code, category) and normalization rules (`normalization.incidentTypes`, plus location/asset/hazard rules) so reports map to it.
2. Add ACTION nodes (phase, `userCanPerform`, `requiresAuthorization`, `canonicalText`, `canonicalKey`, `orderClass`); operational or technical steps are `userCanPerform = false`,
   `requiresAuthorization = true` and phrased "Ask authorized ... to ...". One RECOMMENDATION node per action with a SUPPORTED_BY edge to a source.
3. Wire edges: type TRIGGERS_ACTION action (with conditions: statuses, location types, assets, severity), type PRODUCES_HAZARD hazard MAY_CAUSE consequence REQUIRES_ACTION action,
   location type HAS_CONTINUITY_OPTION arrangement, DEPENDS_ON for prerequisites, OWNED_BY for the responsible team.
4. Validate (`GraphValidator` / `AdminGraphService.validate`) and preview (`preview(incident)`); approve with a real source before ordinary users see it.
With the seed generator: edit `tools/kg_seed/build_seed_pack.py`, run it, and add the scenario to `app/src/test/resources/kg/scenarios.json` (the `SeedPackTest` fixtures).

## Safety rules (spec section 3, enforced in code)
No diagnosis; no medicine, dosage, treatment or home remedy; medical output only first aid already approved, contacting qualified responders, following responders (class
`FIRST_AID_IMMEDIATE`, `CONTACT_RESPONDERS`, `FOLLOW_RESPONDER`), plus the fixed footer for injury cases; no claim that help was dispatched; no invented phone numbers, places,
policies, capacities, exits, equipment or teams (numbers only from VERIFIED, enabled, unexpired contacts; none seeded); never tell an untrained user to enter danger, fight a fire,
handle chemicals, touch electrical equipment or operate shut-offs; human safety first; unverified or expired sources never reach ordinary users; missing facts: abstain and ask.

## Image-only reports (ADR-062)
A report made from photos alone (no narration; every AI value at confidence <= 0.5) is analysed like any other once it is SUBMITTED: on the six sample photos the engine did not abstain (2-3 immediate actions, 2-3 operational steps, 1-4 responsible teams, unresolved question "Was anyone hurt?"). Before submit the engine abstains for every report ("The incident is not confirmed yet."). A foam spill from a toilet (type Spill) gets the chemical-spill action "Stay away from the spilled material": a data gap of the seed pack, not an engine rule.
